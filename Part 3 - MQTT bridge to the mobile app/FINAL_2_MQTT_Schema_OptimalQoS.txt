                          TOPIC HIERARCHY
================================================================================

CORE LOCATIONS TOPICS:
────────────────────

paw/collar/{device_id}/location
  ├─ Description: Real-time collar location (GPS coordinates)
  ├─ Publisher: ESP32 Gateway (receives from LoRa collar)
  ├─ Subscriber: Mobile app (displays on map)
  ├─ QoS: 1 (AT_LEAST_ONCE)
  ├─ Retain: YES
  └─ Update Frequency: Every 30 minutes or on motion trigger

paw/collar/{device_id}/status
  ├─ Description: Collar operational status (battery, signal, last fix)
  ├─ Publisher: ESP32 Gateway (computed from location packets)
  ├─ Subscriber: Mobile app (status bar), Backend (monitoring)
  ├─ QoS: 0 (AT_MOST_ONCE)
  ├─ Retain: NO
  └─ Update Frequency: Every 30 minutes (with location)

paw/collar/{device_id}/heartbeat
  ├─ Description: Collar health telemetry (uptime, cycles, stats)
  ├─ Publisher: LoRa Collar (periodically)
  ├─ Subscriber: Backend logging, Debugging
  ├─ QoS: 0 (AT_MOST_ONCE)
  ├─ Retain: NO
  └─ Update Frequency: Every 24 hours

GATEWAY TOPICS:
───────────────

paw/gateway/{gateway_id}/status
  ├─ Description: Gateway operational status (WiFi, MQTT, LoRa stats)
  ├─ Publisher: ESP32 Gateway (periodic)
  ├─ Subscriber: Monitoring, Dashboard
  ├─ QoS: 0 (AT_MOST_ONCE)
  ├─ Retain: NO
  └─ Update Frequency: Every 30 minutes

paw/gateway/{gateway_id}/heartbeat
  ├─ Description: Gateway alive indicator (uptime, packet counts)
  ├─ Publisher: ESP32 Gateway (periodic)
  ├─ Subscriber: Infrastructure monitoring
  ├─ QoS: 0 (AT_MOST_ONCE)
  ├─ Retain: NO
  └─ Update Frequency: Every 10 minutes

APP TOPICS:
───────────

paw/app/{app_id}/subscribe
  ├─ Description: App subscription/tracking requests
  ├─ Publisher: Mobile app (on startup)
  ├─ Subscriber: Backend (analytics)
  ├─ QoS: 1 (AT_LEAST_ONCE)
  ├─ Retain: NO
  └─ Update Frequency: On-demand

CONFIG TOPICS:
──────────────

paw/config/{device_id}/settings
  ├─ Description: Collar configuration updates
  ├─ Publisher: Backend admin (via gateway relay)
  ├─ Subscriber: Collar (via gateway)

1. LOCATION UPDATE (paw/collar/{device_id}/location)
   ──────────────────────────────────────────────

PURPOSE: Primary tracking data - dog's position on map
CRITICALITY: 🔴 CRITICAL - Must be guaranteed
QoS LEVEL: 1 (AT_LEAST_ONCE) - Broker will retry if app doesn't ACK
RETAIN: YES - New app subscribers immediately see last position
LATENCY: <1 second (WiFi → App)

Example JSON:
{
  "device_id": 1,                    /* Collar ID (0x0001-0xFFFF) */
  "lat": 12.972442,                  /* Latitude (decimal degrees, WGS84) */
  "lon": 77.580643,                  /* Longitude (decimal degrees, WGS84) */
  "ts": 1735689600,                  /* Unix timestamp (when GPS acquired) */
  "battery_mv": 3850,                /* Battery voltage in millivolts */
  "battery_pct": 65,                 /* Battery percentage (0-100%) */
  "accuracy": 4.5,                   /* GPS accuracy radius (±meters) */
  "rssi": -95,                       /* LoRa signal strength (dBm, negative) */
  "snr": 8.5,                        /* Signal-to-noise ratio (dB) */
  "source": "gateway",               /* Data origin: gateway or cellular */
  "gateway_id": "esp32_gw_01",       /* Which gateway received this */
  "num_satellites": 10,              /* GPS satellites used for fix */
  "altitude": 920.5,                 /* Altitude above sea level (meters) */
  "hdop": 1.5,                       /* Horizontal dilution of precision */
  "speed_kmh": 2.3,                  /* Movement speed if available */
  "heading_deg": 145.0               /* Movement direction (0-360°) */
}

MINIMAL REQUIRED FIELDS:
{
  "device_id": 1,
  "lat": 12.972442,
  "lon": 77.580643,
  "ts": 1735689600,
  "battery_mv": 3850,
  "source": "gateway"
}

NOTES:
  • All coordinates in WGS84 (global standard)
  • Latitude: -90 (south pole) to +90 (north pole)
  • Longitude: -180 (west) to +180 (east)
  • Battery %: 0-100% calculated from voltage (3000mV=0%, 4200mV=100%)
  • RSSI is negative (stronger signal = less negative, e.g., -30 > -120)
  • SNR in dB (higher is better, typical 5-15 dB for LoRa)
  • Accuracy is radius in meters (±4.5m = 95% confidence)
  • HDOP > 4 = poor quality GPS fix

QoS RATIONALE (QoS 1):
  ✓ Dog tracking is mission-critical
  ✓ One lost packet = stale location on app
  ✓ QoS 1 guarantees delivery via broker retry
  ✓ App ACKs receipt, broker doesn't resend
  ✓ Overhead: ~12 bytes per message for PUBACK
  ✓ 6 updates/day = 72 bytes overhead (negligible)

RETENTION RATIONALE (RETAIN=YES):
  ✓ App launches → subscribes to location topic
  ✓ Immediately receives RETAINED last message
  ✓ Map shows dog's position INSTANTLY
  ✓ Without retention: blank map for 30 minutes until next GPS fix
  ✓ Storage: ~300 bytes per collar (negligible)
  ✓ UX improvement: Immediate feedback on app launch

2. STATUS UPDATE (paw/collar/{device_id}/status)
   ──────────────────────────────────────────

PURPOSE: Collar health and operational status
CRITICALITY: 🟡 INFORMATIONAL - Nice to have, not critical
QoS LEVEL: 0 (AT_MOST_ONCE) - Best effort, no retry
RETAIN: NO - Status is temporary, changes frequently
LATENCY: Tolerate up to 1 minute loss

Example JSON:
{
  "device_id": 1,
  "status": "active",                /* State: active, sleeping, error */
  "battery_mv": 3850,
  "battery_pct": 65,
  "battery_status": "healthy",       /* healthy, warning, critical */
  "last_gps_fix": 1735689600,        /* Unix timestamp of last fix */
  "last_lora_tx": 1735689610,        /* Unix timestamp of last LoRa TX */
  "gps_fix_quality": "good",         /* good, fair, poor, none */
  "motion_detected": true,           /* Recently detected motion */
  "collar_temperature_c": 28.5,      /* Collar temperature if available */
  "time_since_fix_minutes": 2,       /* Minutes since last GPS fix */
  "lora_rssi_avg": -92,              /* Average LoRa signal strength */
  "ts": 1735689615
}

QoS RATIONALE (QoS 0):
  ✓ Status updates frequently (every 30 min with location)
  ✓ If one message drops, next one in 30 min
  ✓ QoS 0: No retry overhead, saves bandwidth
  ✓ Informational only, doesn't affect core tracking
  ✓ Reduces message count by 50% vs QoS 1

RETENTION RATIONALE (RETAIN=NO):
  ✓ Status becomes stale immediately
  ✓ Showing old battery % on new app launch is misleading
  ✓ App should only show current status
  ✓ Reduces broker storage for temporary data

================================================================================
                        QoS LEVEL RATIONALE
================================================================================

WHY OPTIMAL QoS STRATEGY?
──────────────────────────

Different data types have different delivery requirements:

LOCATION DATA (QoS 1):
┌─────────────────────────────────────────────────────────────┐
│ QoS 1 = AT_LEAST_ONCE (Broker retransmits if no ACK)        │
│                                                             │
│ Critical because:                                           │
│  ✓ Dog lost? Location is the primary tracking data         │
│  ✓ Missing one update = stale position for 30+ minutes    │
│  ✓ App relies on this to rescue lost pet                   │
│                                                             │
│ Costs:                                                      │
│  • Extra 12 bytes per message (PUBACK)                      │
│  • 6 updates/day × 12 bytes = 72 bytes/day per collar      │
│  • For 100 collars: 7.2 KB/day = 216 KB/year (negligible)  │
│                                                             │
│ Benefit:                                                    │
│  • Guaranteed delivery even with network jitter            │
│  • Retained message so new subscribers get position        │
└─────────────────────────────────────────────────────────────┘

STATUS DATA (QoS 0):
┌─────────────────────────────────────────────────────────────┐
│ QoS 0 = AT_MOST_ONCE (No retry, best effort)               │
│                                                             │
│ Acceptable because:                                         │
│  ✓ Status updates with location (every 30 min)             │
│  ✓ If one dropped, next status in 30 minutes               │
│  ✓ Informational only (app shows battery, signal, etc.)   │
│  ✓ Not critical to core tracking function                  │
│                                                             │
│ Costs:                                                      │
│  • None! No ACK, no retry overhead                         │
│  • Saves 50% bandwidth vs QoS 1                            │
│                                                             │
│ Benefit:                                                    │
│  • Lower bandwidth, faster network                         │
│  • Acceptable loss rate for non-critical data             │
└─────────────────────────────────────────────────────────────┘

HEARTBEAT DATA (QoS 0):
┌─────────────────────────────────────────────────────────────┐
│ QoS 0 = AT_MOST_ONCE (Fire and forget)                     │
│                                                             │
│ Acceptable because:                                         │
│  ✓ Published every 10-24 hours                             │
│  ✓ Diagnostic/telemetry only                               │
│  ✓ Backend logging, not needed by app                      │
│  ✓ Missing one heartbeat doesn't matter                    │
│                                                             │
│ Benefit:                                                    │
│  • Minimal overhead for monitoring                         │
│  • Can use for long-term trend analysis                    │
└─────────────────────────────────────────────────────────────┘

RETENTION STRATEGY:
───────────────────

Retain Location (YES):
  WHY:
    • App launches → subscribes to location topic
    • Without retention → blank map until next GPS fix (30 min)
    • With retention → instant position on app open
    • Better UX: Immediate feedback
  HOW:
    • Broker stores last message
    • New subscriber gets it immediately
    • Old message replaced on next publish
  STORAGE:
    • ~300 bytes per collar × 100 collars = 30 KB (negligible)

Don't Retain Status (NO):
  WHY:
    • Status changes every 30 minutes
    • Showing old battery % on new app launch is misleading
    • Status is temporary, not reference data
  BENEFIT:
    • Reduced broker storage
    • App always shows current state

Don't Retain Heartbeat (NO):
  WHY:
    • Heartbeat is periodic ping, not state data
    • Old heartbeat has no value
    • Broker should not store debug telemetry


================================================================================
                        BANDWIDTH COMPARISON
================================================================================

MESSAGE SIZES:

Location update (QoS 1):
  Publish frame: ~300 bytes
  + PUBACK:     ~12 bytes
  Total:        312 bytes

Status update (QoS 0):
  Publish frame: ~200 bytes
  NO PUBACK:    0 bytes
  Total:        200 bytes

Heartbeat (QoS 0):
  Publish frame: ~150 bytes
  Total:        150 bytes

DAILY CONSUMPTION (per collar, 30-minute intervals):

With All QoS 1 (worst case):
  Location: 312 × 6 = 1,872 bytes
  Status:   312 × 6 = 1,872 bytes
  Total:    3,744 bytes/day

With Optimal QoS (QoS 1 location + QoS 0 status):
  Location: 312 × 6 = 1,872 bytes
  Status:   200 × 6 = 1,200 bytes (33% less!)
  Total:    3,072 bytes/day

SAVINGS: 672 bytes/day per collar = ~245 KB/year per collar

For 100 collars:
  All QoS 1:        374 KB/day = 136 MB/year
  Optimal QoS:      307 KB/day = 112 MB/year
  SAVINGS:          67 KB/day = 24 MB/year (18% reduction)

At AWS IoT Core rates ($0.70/GB):
  Savings = 24 MB/year × $0.70/1000 MB = $0.017/year
  (Not significant, but principle is sound: use right tool for job)

================================================================================
                        MOSQUITTO BROKER CONFIGURATION
================================================================================

mosquitto.conf excerpt for PAW system:

# Network
listener 1883
listener 8883
certfile /etc/mosquitto/certs/server.crt
keyfile /etc/mosquitto/certs/server.key

# Authentication
allow_anonymous false
password_file /etc/mosquitto/passwd

# Retention
retain_available true
max_queued_messages 1000

# QoS
max_inflight_messages 20      # Max concurrent QoS 1 messages

# Performance
max_connections -1
max_packet_size 64000         # For larger payloads

# Persistence
persistence true
persistence_location /var/lib/mosquitto/

# Logging
log_dest file /var/log/mosquitto/mosquitto.log
log_type all

# Message expiration (cleanup retained messages)
message_expiration 86400000   # Keep for 1 day (24 hours)

─────────────────────────────────────────────────────────────

acl.conf (Access Control List):

# Gateway access (ESP32)
user gateway_user
topic write paw/collar/+/location   # QoS 1, Retained
topic write paw/collar/+/status     # QoS 0, Not retained
topic write paw/collar/+/heartbeat  # QoS 0, Not retained
topic write paw/gateway/+/status    # QoS 0, Not retained
topic write paw/gateway/+/heartbeat # QoS 0, Not retained
topic read paw/config/+/settings    # QoS 1, Retained

# Mobile app access (read-only)
user mobile_app_user
topic read paw/collar/+/location    # Subscribe QoS 1
topic read paw/collar/+/status      # Subscribe QoS 0 (optional)
topic read paw/collar/+/heartbeat   # Subscribe QoS 0 (optional)
topic write paw/app/+/subscribe     # Send subscription telemetry

# Admin access
user admin
topic read #
topic write #
